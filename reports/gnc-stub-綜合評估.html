gnc-stub 綜合評估

題目：evals/gnc-stub。在隔離的工作目錄寫多旋翼無人機的視覺運動規劃程式 gnc.py，讓 sim.py 的 24 個情境都接觸到目標（滿分 24/24），最後寫 README.md，限時 300 秒。每位考生只取 logs/runs/gnc-stub/ 底下最新一次執行，依大腦分成三組：本地組（Codex、OpenCode、Pi、Qwen Code，本地模型 qwen3.6-35b-a3b，思考關閉）、雲端組（Codex 接 OpenAI 的 gpt-6-luna，思考關閉）與上限標竿（Claude Code，雲端的 claude-opus-5-5）。評估日期 2026-10-09。

測試條件（六位相同）：agent-test.sh 依題目的 ISOLATE 檔，讓 agent 在 /tmp/agent-work.* 作答。sim.py、test_gnc.py 複製進工作目錄並設成唯讀。題目最後附一句「本題限時 5 分鐘，時間到會直接結束，以當時工作目錄的內容評分」。這次對比以 300 秒為基線，每位考生都取限時 300 秒的最新一次。兩位 Codex 用的是同一個 harness，但接的模型不同，所以分開計分、分屬不同組。時間到由 timeout 結束 harness，再用題目原檔的 sim.py、test_gnc.py 對工作目錄裡的 gnc.py 評分，結果記在各 run 的 verify.log。本地組用 --thinking off，四個 harness 各用實測有效的方法關掉思考。雲端組用 --model luna --thinking off，走 Codex 內建的 openai provider，用 ChatGPT 帳號的額度，送出 reasoning.effort=none。Claude Code 沒有關閉思考的方法，照預設執行。
利益揭露：撰寫這份評估的主考官也是 Claude Opus 5.5，和 Claude Code 考生是同一個模型。為了避免偏袒，通過數一律取自 verify.log 的評分結果，不採用考生自己的說法。Claude 的設計與 README 也逐項對照 sim.py 檢查過，失誤照樣列出。另外，三組的模型與思考設定不同，所以只在組內排名，Claude 的分數只當作參考上限。
排名請保守看待。這是每位考生單次執行的結果。本地組四位只差 1 題（0 或 1/24），分數差距主要來自作答過程，而不是成果。本地模型的取樣有隨機性，同一個 harness 重跑可能就換名次。要比較 harness 本身，每位考生至少要跑 3 次再取平均。

設計錯誤與違規

主考官對照 sim.py 的座標慣例檢查交出的 gnc.py，並複製到暫存目錄跑單一情境、看逐拍紀錄確認。行號以交出的 gnc.py 為準。

考生問題影響
Codex垂直方向直接用 v_up = -cy_norm*4（第 140 行），沒有補償 15° 上仰安裝角和機身俯仰錯 全力加速時機身前傾約 35°，同高度的目標在畫面上從 cy=0.80 跳到 0.09，載具誤判而爬升。head_on 停在 8.7 公尺高，從目標下方擦過。
Codex高度下限 4 公尺（第 181–184 行）；前進速度上限 10 m/s，接近時再按估計距離減速錯 碰不到離地 0.75 公尺的目標，far_* 系列都從上方飛過。flee_slow 減速到和目標同速，跟在後面約 6.6 公尺。
Codex跟丟目標的分支先把 last_det 設成 None 再判斷（第 100–106 行）；側向速度符號反了（第 134 行）bug 那個分支永遠不會執行，跟丟後只會以 2 m/s 直飛；目標在左時反而往右移。
OpenCodeyaw_rate = -cx_offset/fx*k（第 112 行），第 108 行的註解寫「向左轉（yaw_rate > 0）」錯 sim.py 規定 yaw_rate 順時針（右轉）為正。目標偏左時反而右轉，形成正回授，飛機在原地打轉。濾波初值設 0 像素，第一拍就卡在 60°/s 上限。
OpenCodev_up 恆為 0；中遠距離 v_fwd 只有 5 m/s設計不足 主考官只修正偏航符號，結果是 2/24；其餘情境被高度與速度擋住。
Pi搜尋分支用到沒定義的變數 v_right（第 230 行）崩潰 目標一離開畫面就丟出 NameError，24 題裡有 22 題崩潰。這個版本在時間到前 0.3 秒寫入，從沒跑過。
Piyaw_rate 用 math.degrees() 送出；安裝角用正轉公式來反轉；把 FLU 向量乘上 FRD 的旋轉矩陣錯 偏航增益放大 57 倍，變成貼著上限的開關式控制。視線方向差約 30°，垂直方向反了：中間版本 13 題墜地，就是這個原因。
Qwen Code條件寫 len >= 2，卻讀 det_history[-3]（第 160 行）崩潰 第二拍就 IndexError，24 題全部崩潰。主考官只修這一行，結果是 1/24，另有 7 題墜地。
Qwen Codecx 偏右時輸出負的 yaw_rate 和 v_right；安裝角算了沒用，把目標拉向光軸中心錯 左右反向；同高的目標本來就在光軸下方 15°，載具會一路往下飛。
Codex（Luna）side = clamp(-8.0 * az, ...)（第 34 行），az 在目標偏右時為正錯 目標在右邊卻往左平移。cross 一開始 cx=0.47（偏左），下的卻是 v_right=+0.38。偏航率（第 36 行）的符號是對的，所以兩者互相拉扯。
Codex（Luna）仰角只加上安裝角（第 30 行），沒用 att 扣掉機身俯仰錯 加速前傾時，目標仰角被高估，載具一路爬升：cross 爬到 17 公尺，far_static 爬到 14.3 公尺。head_on 從目標頂上 0.285 公尺處掠過。
Codex（Luna）前進速度 = 0.18 ×（估計距離 − 1.5），上限 13 m/s（第 38 行）；跟丟時偏航率與升降都歸零，4 秒內把前進命令衰減到 0（第 19–24 行）錯 沒有目標速度前饋：flee_slow 以 2 m/s 跟在後面約 17 公尺，追不上 14–15 m/s 的目標。目標一出畫就不再搜尋，最後原地懸停到 90 秒。
Codex（Luna）README 寫「水平像素偏差同時產生偏航率及側向速度命令，以將目標拉回畫面中央」說法不實 側向速度的方向其實相反。逐題數字和 verify.log 完全一致，但失敗分析大多是泛論（「末端控制不足」），沒點出沒扣俯仰、側向符號、跟丟後懸停這幾個真正的原因。

給 harness-lab 的附帶發現

  • 5 分鐘對本地組太緊：本地模型生成約每秒 35 token，整檔重寫一次 gnc.py 要 1–2 分鐘，四位都只來得及寫兩輪，沒有人留時間寫 README。如果想看本地組能不能把這題做出來，可以另跑一組較長的限時；如果想看時間管理，就維持 5 分鐘。
  • 座標慣例是共同弱點，不只本地組：六位都讀完了 sim.py。本地組三位寫出左右或偏航符號相反的控制，四位都沒有正確補償 15° 安裝角。Codex（Luna）也一樣：側向符號反了、沒扣機身俯仰。sim.py 開頭的文件字串把慣例寫得很清楚，問題出在寫程式時沒有回頭核對。只有 Claude 把整條換算寫對。
  • 「時間到前一刻覆寫」是新的失敗模式：Pi 讓一個能過 1 題的版本，被沒跑過的版本蓋掉。題目可以提示「改版前先另存檔案，驗證過再換上」，或讓 agent-test.sh 記錄每次寫入的版本，方便事後分析。
  • 兩個雲端模型都太早收尾：Claude 在第 64 秒、Codex（Luna）在約第 95 秒就開始收尾，分別剩下 233 秒、196 秒。Claude 還說是因為時間不夠；Luna 只過 1 題，也沒說明為什麼停。模型看不到經過了多久，所以會高估自己用掉的時間。題目可以說明怎麼看經過時間（例如用 date 對照開始時間），或由 harness 在工作目錄放開始時間。
  • 隔離的漏洞：/tmp 是所有執行共用的，六位裡有四位把 trace 寫在那裡，還有同名目錄被不同次執行重複使用。建議在 agent-test.sh 給每次執行獨立的 TMPDIR，或在題目裡要求 trace 寫在工作目錄內。
  • 語言要求：Codex、OpenCode、Pi 的過程回覆都是英文。思考關閉後，本地模型多半沒有照題目要求使用繁體中文；Qwen Code 和 Codex（Luna）全程用繁體中文。
  • Luna 這一輪是在思考關閉下跑的，不代表它的上限。如果想把它當成第二個標竿，應該再跑一次不加 --thinking off 的版本。

結論

本地組四位都讀完了模擬器，但在 5 分鐘內沒有人寫出能接近目標的程式：Codex 1/24，其餘三位 0/24，其中 Pi、Qwen Code 交出的程式會崩潰。分數差距主要在交出的東西能不能跑：Codex 和 OpenCode 交出能執行的程式，排第 1、2 名；Pi 在最後一刻把能跑的版本蓋掉，Qwen Code 從沒有一個版本跑得完，排第 3、4 名。

這一題的難點在把目標框換算成世界座標的視線：要用上相機內參、15° 安裝角與飛控姿態。本地組沒有人做對，所以只能拿像素偏移做比例控制，結果不是打轉、墜地，就是追不上。換 harness 補不了這一點，這是模型能力的差距。

Codex（Luna）用同一個 harness 換了雲端模型，成績還是 1/24，和本地組的 Codex 相同。差別在節奏與交付：每輪只要幾秒，104 秒就交出能跑的程式和誠實的 README。但換算的錯誤類型和本地組一樣，而且在剩下三分之二時間時就停了。思考關閉下的 Luna 在這題沒有比本地模型好多少，反而凸顯 Claude 寫對座標換算的價值。

Claude 一次就寫對換算，67 秒做到 20/24，但沒用完限時就收尾，還把原因說成時間不夠。所以 20/24 不是它的上限，比較像是它沒把題目做完時的成績。
