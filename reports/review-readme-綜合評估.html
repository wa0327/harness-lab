ds4 組的請求沒有經 logproxy，所以沒有系統提示的紀錄。依 agent.jsonl 核對，兩位的工具呼叫全部在快照內。

給 harness-lab 的附帶發現

  • 開源模型的審查都會出錯：本地組每份報告有 1–3 條錯誤或捏造，ds4 組有 1–2 條。大多是「README 已經寫了卻說沒寫」或「沒查證就下結論」，Codex（ds4）對 --fit off 的解釋則是用猜的。用這些模型做文件審查，結論一定要人工核對。
  • 換成較強的模型，Pi 進步最多：同樣是 Pi，用本地模型時只呼叫 3 次工具就交差；換成 ds4 後呼叫了 11 次，加權命中從 1 升到 6，分數從 46 升到 56。Codex 用兩種模型都會讀腳本，換模型後主要差在覆蓋（加權命中從 3.5 升到 9）。
  • 單次結果不足以比較 harness：建議每位考生跑 3 次取平均，報告改成「平均分數 ± 範圍」。
  • 這一題的鑑別力不錯：第 2、8、13 條七位都漏了，第 11、12、15 條只有 Claude 抓到，可以留著比較日後的模型或設定。

結論

本地組四位都待在快照內，在 2–3 分鐘內交出報告，分數落在 46–57 之間。差距主要是有沒有認真探索專案：Codex、Qwen Code 讀了腳本和設定，抓到的是專案特有的問題；Pi、OpenCode 讀得少，寫出來的就是放到哪裡都成立的通用清單。

ds4 組兩位（Codex 60、Pi 56）都比本地組同一個 harness 的分數高，多出來的分數主要在覆蓋和正確性：Codex 抓到 36 對 38 會 OOM、Qwen Code 一節沒寫思考，Pi 抓到 router 不適合跑 FIM。代價是時間，在遠端主機上要 9–14 分鐘，本地組只要 2–3 分鐘。

和 Claude 比，差距縮小了，但還很明顯：覆蓋是 21 分對本地組的 1–5 分、ds4 組的 6–10 分，錯誤是 0 條對 1–3 條。需要推演腳本實際行為才看得出的問題（第 11、13 條），兩個開源模型組的六位都沒抓到。這是模型能力的差距，換 harness 補不回來。
